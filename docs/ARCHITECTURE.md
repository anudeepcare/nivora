# AURYN application architecture

This standalone Next.js application is under `product/` in the existing repository, or is the extracted ZIP's application root. No legacy components, CSS, engines, routes or dependencies are imported. Brand assets are retained. The existing authenticated account tables remain compatible; migrations are additive.

- **UI:** React account boundary → four primary destinations → inline company tabs. Light/dark design tokens and responsive CSS are authored in one stylesheet. Search and navigation use client transitions. Chart gestures do not capture page scrolling; zoom is explicit. Private client caches are scoped to the verified account and cleared on logout.
- **Identity:** Each API verifies the Supabase access token using `auth.getUser`. User IDs are derived from this verified response. Ordinary writes use the user's JWT and row-level security. Execution requires trusted app metadata/admin configuration plus one explicit broker-account owner UUID. Editable user metadata is not authorization.
- **Data:** Twelve Data supplies quotes and OHLC; SEC companyfacts and submissions supply reported evidence; optional Finnhub supplies profiles, earnings and classified insider activity. Server keys never enter client bundles. Prices retain currency, session and as-of information. Missing observations stay null.
- **Calculations:** `engine.ts`, `research-depth.ts`, `analysis.ts`, `scenarios.ts` and `technical-depth.ts` implement original transparent policies. Corporate facts and technical timing remain distinct. Monthly multipliers are experimental price zones, not a validated personalized investment recommendation. All model families have explicit coverage boundaries.
- **Snapshot:** `canonical.ts` assigns an evidence identity to evaluated history and facts, and a snapshot identity that also includes quote state. Dated observations are immutable to ordinary authenticated users. These are decision records, not a complete licensed point-in-time historical database.
- **Persistence:** Base account tables, saved documents, alert events, observations and service-controlled paper audit tables are created by ordered migrations. Import IDs prevent a retry from duplicating holdings. Original documents may be edited; observations cannot be overwritten by clients.
- **Cost control:** Provider request deduplication and caching, bounded screens, portfolio quote batches, 55 total Twelve Data requests/minute and 42 background requests/minute. With service-role credentials the budget is database-wide; otherwise it is process-local. Commercial deployment must set `AURYN_REQUIRE_DISTRIBUTED_BUDGET=true`. Paid AI is opt-in, three requests/account/day and one hundred globally/day; these are request quotas, not guaranteed dollar ceilings.
- **Paper execution:** Fixed `paper-api.alpaca.markets` host, explicit whole-share limit-day plans, regular-session checks, fresh quotes, no shorting or borrowing, cash reserve and concentration caps. An atomic account-wide lock and unique plan/month/client IDs precede submission. Account state is checked again inside the lock. Ambiguous submission stays reserved until reconciliation; no automatic resubmission. Broker fills are authoritative. These are owner-defined plans, not canonical-engine-driven autonomous trading.
- **Operations:** `/api/jobs` accepts only a configured high-entropy bearer secret. It evaluates the configured alert owner and bounded configured paper-owner plans. The supplied workflow is manual by default. No live database migration, hosted deployment, paid AI call or brokerage order was performed while building this source.

The client keeps existing content during most refreshes. Large portfolios load progressively in batches of 20 with provider headroom; this intentionally does not promise tick-by-tick updates for hundreds of symbols on the existing allowance.
