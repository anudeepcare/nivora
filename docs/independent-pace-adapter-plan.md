# Trusted adapter: next steps, not completed work

## Current reusable data paths and gaps

- `eodRequest` / `sharedEodRead` provide server-side authorized EODHD fetching, cache/budget/backoff behavior. Extend an evidence envelope to retain original fetched-at time and request identity through cache hits; do not invent a fresh provider observation time when reading cached data. Never persist API tokens in evidence references.
- `provider-symbol` and `eodTicker` route supported US share aliases. The independent adapter must preserve both provider composite identity (for example a `.US` route) and actual listing venue. They are not interchangeable. Confirm identity from raw General fields and requested route before normalization.
- Existing `eodHistory` / `normalizeEodBars` construct split-adjusted raw OHLC. They are NOT the prototype's required split-and-dividend-adjusted close series. Read one complete raw `eod` window and use only `adjusted_close`, with the current settled observation from that same response. Never splice current unadjusted real-time quote into adjusted history. `account-benchmark` demonstrates strict adjusted-close/duplicate validation without classifier dependencies.
- `Company.assetType` is only stock/crypto; search treats ETFs, preferreds, ADRs and REITs as stock. It is not sufficient to establish common-equity eligibility. Raw instrument type, listing status, currency, code and venue must survive in the evidence envelope. Absent or contradictory values withhold eligibility.
- `normalizeEodFundamentals` substitutes retrieval day for absent `filing_date`. A generic normalized `Fact` therefore cannot prove point-in-time availability. Preserve explicit reported/publication date versus fallback status at ingestion; reject missing publication dates for historical eligibility. Today's provider statements may be revised and are not a point-in-time archive.
- `calendar.ts` handles US month-end scheduling only. It does not establish the latest settled daily session, early close, exceptional closure or provider publication completion. Do not treat it or weekday-based quote session labels as a complete exchange calendar.

## Bounded implementation sequence

1. **Pure raw-data adapter plus immutable evidence envelope.** Require requested identity, verified raw profile, same-fetch adjusted daily history, original retrieval timestamp, as-of instant, explicit policy and external verified session schedule. Reject duplicate/conflicting dates, nonfinite/nonpositive closes, mixed instruments/units, gaps at required session endpoints, incomplete current session, and unknown listing status/type. Compute each completed monthly close from the exact last expected session; withhold if missing. Never shift missing data to a nearby date. Hash normalized authorized evidence for reproducibility without storing credentials.
2. **Independent eligibility assessment, separate from price depth.** Implement observable universe/data gates first: verified supported active common-equity listing; known USD pricing for the initial app scope; sufficient adjusted history; dated coherent statements where policy requires them. Unknown is a third state, not false/zero. Emit every gate, source, date and reason. Do not call these checks business quality or investment suitability. Business-policy rules must be an explicitly specified independent configuration with required metrics and permitted thresholds; do not import the app's old pass/mixed/fail score or calibration constants. If no approved business policy exists, result remains unknown and no stage is emitted. Derive comparable revenue, operating income, cash flow, equity/debt evidence only from dated same-basis periods, keeping source references and missingness; calculations alone do not determine a buy/add decision.
3. **Verified exchange-session provider and authorized integration.** Supply an official/current session schedule including timezone, holidays, early closures and exceptional closures, with a defined provider-publication completion policy. Required current session depends on as-of instant, not simply UTC date. Unknown schedule or delayed publication withholds results. Fetch through existing rate-limited service only after provider contracts/entitlements are checked. Initial integration is offline/shadow evidence only, never production replacement.

The current prototype's same-calendar-month restriction can withhold on the first day of a month before its first settled session. This conservative behavior is preferable to silently switching basis; any later support for prior-month observations must be explicit and separately tested.

## Verification required

Synthetic adapter fixtures: raw/adjusted divergence; split and dividend days; symbol aliases and cross-listing mismatch; ETFs/preferreds/delisted instruments; absent status; duplicate/dropped sessions; weekend/holiday/month boundary; DST and early close; future quote, missing/late provider close; cached stale data; incomplete monthly endpoints; missing or revised publication dates; absent/mixed-currency statements; ineligible versus unknown; numerical overflow.

Authorized provider smoke checks: retrieve a small declared sample spanning ordinary stock, share class, recent listing and corporate action; confirm raw identity/currency/status and adjustment contracts against provider documentation; reconcile exact sessions and dates. No restricted third-party verdicts, labels or fitted parameters are used. A current API snapshot cannot establish historical point-in-time validity.

Independent review must verify both code and evidence provenance. Financial behavior must be assessed separately using authorized data and an independently chosen policy, including declining businesses and rising markets where price-quantile bands are misleading. A software test pass is not investment validation. No production switch until a deliberate release decision follows that review.

## Work estimate, not a promise

A narrow inactive US/USD raw adapter plus synthetic tests and evidence gates is roughly 3–5 focused engineering hours once field contracts are verified. Session-calendar integration and provider smoke checks add roughly 2–4 hours if a complete licensed/official schedule and account access are already available; otherwise that dependency blocks trustworthy freshness. Independent financial-policy design, historical point-in-time data acquisition and out-of-sample validation are separate work and cannot honestly be bounded to the same day from the current evidence. The immediate deliverable should be auditable data/evidence, not a rushed replacement signal.

## Blockers versus safeguards

**Blocking trustworthy data adaptation:** raw adjusted-price field contract and same-snapshot provenance; verified security type/status/venue rather than the lossy Company type; complete authoritative session schedule and publication-completion rule; original cache retrieval provenance. Until each is implemented and tested, affected instruments return unavailable. Missing account entitlement or a usable session source is an external dependency, not a UI problem.

**Blocking a meaningful independent financial signal:** an explicitly chosen independent business policy, explicit lookback/quantile choices and their rationale, point-in-time financial availability for any historical claim, and independent behavior/out-of-sample validation. No amount of additional UI testing resolves these. Even a fully trusted data adapter is not enough to activate a financial stage.

**Already implemented safeguards in the inactive prototype:** required non-default policy, recognized currency and matching declared instrument identity, positive finite inputs, strict chronological completed-month window, latest-declared-session match, source/calendar/eligibility evidence references, fail-closed unknown/ineligible state, unavailable rather than invented data, exact thresholds and dates, and universally null trade instruction/unvalidated status. These checks constrain a caller; they do not authenticate the caller's claims.

**Planned safeguards, not external blockers by themselves:** immutable evidence envelopes, hashes with secrets excluded, explicit missing-date provenance, session-by-session completeness checks, gate-by-gate explanations, offline shadow comparison of own calculations, synthetic regressions, independent review and deliberate release gate. Implement them before integration; do not present planned checks as completed protection.

## Milestone 1 implemented: inactive evidence collector

`independent-pace-adapter.ts` now validates raw common-stock identity/type, explicit non-delisted flag, supported US venue, USD currency and one complete returned adjusted-close snapshot. It rejects malformed/conflicting/duplicate/unsorted/out-of-window rows rather than falling back to raw close. It preserves provider composite ticker separately from actual venue, snapshots the request across asynchronous reads, freezes normalized evidence and records a reproducible normalized-evidence SHA-256 hash. The hash detects changed evidence; it does not authenticate provider origin.

`independent-pace-adapter.server.ts` binds this collector to existing `eodRequest`, preserving its authorized cache, quota and backoff paths. It is not imported by any application route or component. There are at most two provider requests per invocation, profile first, then prices only after supported identity checks. These are requests, not a promise of two API credits: provider billing weights may differ. Resource bounds are an explicit 3,660-day window and 4,000 returned rows, not financial model parameters. Unsupported/unknown identity stops before the price request. Errors are sanitized, and there is no fallback or cache bypass.

The result is ALWAYS `readyForPace: false`, `stage: null`, `instruction: null`. Valid fields yield `evidence-only`, never “trusted” or “ready”. Original cache-fetch time is explicitly null; read time is separately labeled; session calendar is unverified; business eligibility is unknown. Sparse history can be retained as evidence but cannot become a completed monthly series or classifier input. No data was fetched during implementation; tests use synthetic payloads and inject the reader. No new credentials, paid subscription, route, deployment or scheduled collection was created.

Provider contracts checked against official documentation: [fundamentals](https://eodhd.com/financial-apis/stock-etfs-fundamental-data-feeds), [daily adjusted-close data](https://eodhd.com/financial-apis/api-for-historical-data-and-volumes). Payload fields still require live authorized smoke verification before making a trust claim. Missing `IsDelisted` fails closed rather than inferring active status.

Remaining blockers above are unchanged: authenticated evidence-envelope timestamps, authoritative sessions/publication completeness, independent business-policy implementation and financial validation. This milestone narrows the raw-data interface; it does not solve them.

## Independent review release boundary

The reviewer found no blocker for this inactive evidence-only milestone (seven adapter tests independently passed). This is not approval to expose it. Before any route/action/UI consumer is added, enforce per-user authentication and dataset entitlement in the server entry, then add and verify a compile-time server-only module boundary. The current `typeof window` check is runtime-only; the `.server.ts` filename and use of Node crypto do not substitute for a framework-enforced server-only boundary. The shared provider key and shared rate limit do not establish an individual user's entitlement. Do not expose a reader-injection interface to clients. Verify authorization failures spend no provider credits and reveal no data. Until those checks, trusted provenance, calendar and business-policy gates are implemented, preserve zero runtime consumers and never describe the collector as working Pace.

## Milestone 2: source-only cache provenance inspector

`cache-evidence-provenance.ts` validates separately supplied cache-owned metadata without changing the payload or existing cache behavior. Legacy bare payloads receive `unknown`, with no origin timestamp invented. A versioned metadata record must match the exact request key and a canonical-JSON payload hash, carry strict nonfuture UTC fetch/expiry times, and satisfy an explicit caller-selected maximum age. Equality with either expiry limit is stale. Repeated reads never reset the declared origin. Key ordering changes (such as JSONB serialization) do not change the fingerprint; altered values do. Nonfinite, non-JSON or cyclic payloads have no fingerprint.

A consistent record is only `within-declared-window`, not authenticated fresh data. `mayUseForPace` remains false in every case. Metadata is never inferred from fields inside a provider payload. The inspector is not wired to caches or endpoints and has no network/database side effects.

**Architectural blocker:** the existing local cache stores bare promises of payload; the shared acquire RPC returns bare payload; its database `updated_at` records publish time; and the upstream `fetch` may itself be satisfied by Next revalidation caching. Stamping either read or publish time cannot establish actual provider-origin fetch time. Therefore this milestone does not produce origin metadata for existing entries. It reports unknown instead.

A future origin-aware transport must produce a versioned evidence envelope at a verified network response, preserve that envelope through every cache layer, distinguish actual origin receipt from provider market observation time, and retain unknown for older entries. That requires deliberate cache-key/schema compatibility and transport design, with budget/lease/TTL tests and independent review. A SQL publish timestamp alone, HTTP success alone, a hash alone, or a caller-set origin flag is not adequate authentication. No cache bypass, database migration, schema change or duplicate provider collection was performed here.

## Inspector review caveats and safe origin design

The inspector deliberately preserves the caller's payload identity to avoid altering existing cache semantics. That payload can be mutated after inspection: its previously checked hash does not establish future integrity (a time-of-check/time-of-use risk). Before any trusted consumer exists, take an immutable JSON snapshot, calculate and bind metadata to that snapshot, and keep the validated snapshot rather than continuing to use mutable references. Metadata here is unsigned and caller-supplied; matching hashes and timestamps prove internal consistency only. A trusted cache-owned acquisition path, not a request parameter or provider-body field, must create the origin record. Independent review approved only this inactive inspector scope.

A feasible origin-aware design, NOT implemented:

1. Create a separately versioned server-only evidence path after per-user authentication and entitlement. Do not retrofit a timestamp onto a bare old-cache hit. Preserve existing ordinary payload APIs byte-for-byte and retain unknown provenance for old entries.
2. Route that path through the same account-wide weighted budget, reservation and backoff controls, using a deliberately namespaced evidence-cache key. Namespace changes can cause a second provider acquisition alongside old caches, so explicitly test and disclose this cost, prevent dual old/new loads for one consumer, and do not enable background warm-up. Do not encode an internal namespace as an upstream API query parameter.
3. On an actual reserved acquisition, use an explicitly uncached transport for this new path only. A callback using current Next revalidation caching cannot certify origin. Record response-received time from a trusted server clock after receiving the provider response, then parse/validate and take an immutable JSON snapshot. This time is receipt from the provider service/edge, not the date the underlying market observation was generated; preserve and check those separately. Provider/CDN caches can still serve stale market observations.
4. Store a versioned envelope containing the immutable snapshot, exact route/parameters excluding secrets, currency/instrument/adjustment provenance, received-at time, expiry, schema version and payload hash. Preserve the same envelope through local, shared and framework layers without rewriting its receipt time on hits or publish. Cache expiry is not source freshness. Never add a fresh timestamp when adapting a legacy bare entry.
5. Keep account-budget identity separate from any user-visible evidence references. Namespace/hash construction must exclude API tokens and not leak shared account identity. Enforce per-user authorization before consulting shared evidence; a shared cache hit must not bypass entitlement.
6. Tests/review before any shared-cache edit: old API outputs unchanged; one network acquisition under concurrent leases; cache-hit receipt time unchanged; legacy unknown; rejected/paused/budget-limited requests never acquire; publish failures and expired leases; clock skew/future timestamp; stale provider session despite recent receipt; hash mismatch; immutable snapshot mutation attempts; credential redaction; and authorization denial without data/credit spend. Test database migrations in local isolation before any deployed schema change.

This design changes the new path's transport/caching behavior and may require a versioned shared-cache interface. It is not a “safe one-line timestamp fix.” No shared cache, transport, RPC, schema, budget or endpoint changes were made in this milestone.
